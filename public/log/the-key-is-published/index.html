The key is published

Last week ended with "that's next." This week it's done, along with one secret I didn't name last week. And I found two places still vouching for the old key.

By William Shane Wilkinson · Salt Lake City · Approx. 4 minutes

Last week's log ended on an open item: our new public key wasn't published yet, so checking one of our new records meant taking our own server's word for which key is ours. I said that was next. It's done. The key is on our protocol page, next to the keys it replaced.

This is the third log in a row about one breach at our hosting provider. I'm writing it anyway, because a promise in public is only worth something if the follow-up is in public too.

The secret I didn't name

Last week I wrote that "a few steps are left" and didn't say which. One of them was the password to our database. It was stored with the host, so by the host's own advice it had to be treated as stolen, and the database can be reached from the internet. Saying in public that it hadn't been changed yet would have told anyone holding it that it still worked.

It's changed now. Its connection details are written into several places, so I didn't trust any of them to follow on their own. I changed them first and checked that every one had picked up the new password before the database itself changed. Then the new password connected, the old one was refused, and the service restarted on the new one. For a few minutes the service couldn't open new connections, which was planned. Afterward a record from July still verified, a made-up code was refused, and nothing in the chain moved.

Two places still vouching for the old key

Publishing the key is where this week's real lesson came from.

Our protocol page has a section that lists the keys we sign with, so anyone can check a record against them instead of trusting us. When I went to add the new key, that page still described the old one as the key that "signs registry-asserted records today." It had said that for eleven days after the old key was retired. The page whose whole job is to tell you which key to trust was wrong about which key to trust.

The second was our own shipping check for TamperVerify seals. Before a box closes, it checks that every seal in it was signed by the current key. It still had the old key written in as current. That one failed safe: it would have refused every new seal rather than passing a bad one. But it meant we couldn't have shipped a newly registered seal until someone noticed.

Neither was dangerous. Both are the same mistake: replacing a key changes the place that uses it, not the places that describe it. When I wrote the rotation plan I listed what reads the key. I didn't list what tells other people about it.

What changed

The protocol page now lists the new key as current. The old one is listed as retired, with what happened and where its limit sits: records it signed before stay valid, and nothing new can be signed with it. The August key is still there too. Retired keys don't come off the list, because the records they signed still need checking.

What's left

The rail hasn't yet recorded anything signed by the new key. When it does, I'll check that record against the published key myself. A couple of account cleanups on the host's side are also still open.
